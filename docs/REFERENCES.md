## 3. 引用方式与合规红线

1. **物理隔离**：所有第三方参考仓库统一存放在 `references/<project-name>/` 下，由 `.gitignore` 忽略，绝不混入主仓库提交历史。
2. **设计借鉴而非代码搬运**：
   - 允许学习参考项目的架构边界、状态机设计、威胁分类模型与测试用例设计思路。
   - **禁止**直接拷贝第三方代码文件或函数实现进入 `apps/` 与 `packages/`。
3. **合规声明**：若未来确需在某个独立模块中合法引入兼容许可证的开源代码片段或规则字典，必须提前确认许可证兼容性，并在对应文件头部及项目 `NOTICE` 文件中完整保留原版权声明与许可证文本。

## 4. AI卫士自身开源许可证推荐方案（待确认）

根据任务要求，当前**不自动生成**根目录 `LICENSE` 文件。结合 AI卫士“**个人版开源免费 + 未来推出企业商业版（Open-Core / 双轨商业模式）**”的产品定位，提供以下三种主流方案供决策：

### 方案 A：Apache License 2.0（优先推荐）

- **适用场景**：个人版核心仓库采用宽松开源协议，最大化吸引开发者社区采用与贡献；企业版（集中管理控制台、企业策略中心、多租户审计）作为独立闭源商业仓库或独立模块开发。
- **优势**：
  1. 包含明确的专利授权条款与商标保护条款，法律界限清晰。
  2. 与参考生态（如采用 `Apache-2.0` 的 HOL Guard、Codex 等）天然高度兼容。
  3. 个人版用户和企业客户对 Apache-2.0 接受度最高，无传染性顾虑，有利于个人版快速推广。
- **注意事项**：需在架构上确保个人版开源仓库与未来企业版专有代码保持清晰的仓库/模块物理边界。

### 方案 B：MIT License

- **适用场景**：追求极简、最宽松的开源授权。
- **优势**：条款极其简短，几乎无使用门槛。
- **注意事项**：缺乏 Apache-2.0 中显式的专利授权与专利报复条款，也无显式商标免责声明，对于安全类基础软件而言，法律保护力度略弱于 Apache-2.0。

### 方案 C：MPL 2.0（Mozilla Public License 2.0，文件级弱传染开源协议）

- **适用场景**：希望开放个人版源码，同时要求外部如果直接修改了 AI卫士的既有开源源码文件，必须将修改后的文件同样开源，但不影响其通过接口动态链接私有模块。
- **优势**：兼顾开源共享与防止竞争对手直接拿走核心文件闭源魔改。
- **注意事项**：需注意未来若吸收 GPL/AGPL 类项目时的许可证冲突问题（严禁引入强传染性的 GPL/AGPL 代码进入核心库）。

### 法律与合规建议汇总

1. **推荐首选**：建议个人版主工程采用 **Apache License 2.0**。
2. **第三方避坑原则**：在后续引入 `nono`、`Pipelock`、`Agent Sessions`、`SessionVault` 等参考项目前，必须先核查其 `LICENSE`：
   - 对 `MIT`、`Apache-2.0`、`BSD` 类项目：可安全参考设计。
   - 对 `GPL`、`AGPL`、`SSPL` 或无许可证（No License / All Rights Reserved）项目：**严禁**复制任何代码或衍生实现，仅可通过公开文档了解其黑盒功能概念。
3. 待项目负责人确认最终许可证类型及版权署名主体后，再正式创建根目录 `LICENSE` 文件。
