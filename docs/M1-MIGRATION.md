# M1 阶段既有成果迁移计划（M1 Migration Plan）

## 1. 背景与迁移原则

在启动当前独立的 **AI卫士（AI Guard）** 新工程之前，M1 阶段已在历史工程中完成了部分 **Codex Session 管理** 相关代码的研发与验证。

为确保新工程架构整洁、边界清晰且不影响历史工程，制定以下迁移原则：

1. **原工程只读不改**：严禁直接修改、重构或删除旧 M1 工程中的任何文件。
2. **不盲目全量复制**：不将旧工程整体复制覆盖到新仓库，而是按照新工程 `packages/session`、`packages/backup`、`packages/storage`、`packages/agent-adapters` 的职责边界进行模块化拆解与迁入。
3. **先建契约与测试，再迁实现**：迁入代码必须符合新工程的目录结构、异常处理规范及只读安全原则，并补齐自动化测试验证。

## 3. 目标模块映射方案

待提供原 M1 工程路径后，原有代码将按职责拆分映射至新工程的以下模块：

| 原 M1 功能域 | 新工程目标路径 | 迁移与改造要求 |
| :--- | :--- | :--- |
| Codex 会话目录定位、Codex 专属字段格式解析 | `packages/agent-adapters` | 抽离 Codex 专有的路径探测与原始格式转换逻辑，避免将 Codex 特有细节硬编码在通用 Session 管理层中。 |
| 会话模型定义、会话索引、检索、详情组装、导出与清理编排 | `packages/session` | 保持对原始活跃会话文件的**只读访问**；任何删除或清理动作必须先调用 `packages/backup` 接口。 |
| 会话文件备份、恢复与校验逻辑（如有） | `packages/backup` | 统一收敛至 `packages/backup`，强制补齐 SHA-256 哈希完整性校验与原子恢复机制。 |
| 本地 SQLite 表结构或缓存文件读写（如有） | `packages/storage` | 剥离零散的文件/数据库直接读写代码，统一收口到 `packages/storage` 的持久化访问层。 |
| 原有单元测试与样本数据 | `tests/` | 脱敏处理所有测试样本（剔除真实路径、个人隐私指令与密钥），迁入 `tests/` 作为回归测试基准。 |

## 4. 标准迁移执行步骤（下一阶段专项任务）

1. **步骤一：路径确认与只读盘点**
   - 由用户提供原 M1 工程的准确本地路径。
   - 扫描原工程目录结构、依赖项（如 Python 版本、第三方库）及现有测试用例，输出盘点清单。
2. **步骤二：接口与数据模型对齐**
   - 核对原 M1 的 Session 数据结构与新工程 `packages/session`、`packages/storage` 的接口边界。
3. **步骤三：分模块迁入与解耦改造**
   - 依次迁入存储层、Codex 解析适配层、Session 业务层代码。
   - 检查并消除任何跨模块直接读写文件或异常静默吞没的问题。
4. **步骤四：验证与回归测试**
   - 运行迁移后的单元测试与真实/模拟 Codex Session 目录只读解析验证。

---

## 5. 迁移验收要求

M1 成果迁移完成时必须满足以下验收标准：

1. **零破坏性验证**：对本地 Codex 会话目录执行百次以上读取与索引操作，原会话文件的内容、权限与修改时间（mtime）保持零篡改。
2. **异常鲁棒性验证**：面对半写入状态（正在进行中的 Session）、损坏的 JSONL 行或空文件时，解析器能够安全跳过或局部降级，不引发服务崩溃。
3. **敏感操作闭环验证**：涉及会话清理或归档的功能，必须验证已前置生成备份且备份文件通过 SHA-256 校验。
4. **旧工程完好确认**：原 M1 工程目录的 `git status`（或文件校验和）在迁移前后完全一致。
